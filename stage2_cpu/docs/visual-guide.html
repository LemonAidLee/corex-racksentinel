01

The cast, as a kitchen

One analogy carries the whole design. A CPU is a single cook working through a recipe book, one line at a time, with a fixed set of tools on the counter. Every block on your canvas is one role in that kitchen.

  • 📕The recipe book on the wall IMEM_FIRMWARE Read-only. Holds the program — and an appendix of constants at the back.
  • ☝️Your finger on the line PC_Unit Remembers which line you're on. Moves once per dish, not once per beat.
  • ➕Sliding down one line PC_Unit Instructions are 4 bytes, so "next" is always address + 4.
  • 📝The sticky note Datapath_Mux You copy the line down, because your finger is about to point elsewhere.
  • ✂️Highlighting the sentence Datapath_Mux Pulls out verb, ingredient A, ingredient B, output bowl.
  • 👨‍💼The manager Control_Unit Reads the order and shouts 14 commands per beat. The only real brain here.
  • 🥣32 labelled prep bowls Register_File x0–x31. Bowl 0 has a hole in it — always empty, by design.
  • 🔪The chopping station alu Add, subtract, AND, OR, shift, compare. Everyone borrows it.
  • 🌀The heavy blender MULT_Unit Specialist. Too expensive to fold into the chopping station.
  • 🏷️The checksum stamper CRC16_Unit Your team's custom instruction. A data fingerprint in one cycle.
  • 🔢The number in the recipe IMM_GENERATOR Digs the constant out of the instruction and sign-extends it.
  • ⚖️The taster BRANCH_COMPARATOR Answers one yes/no: are these two bowls equal? less? greater?
  • 📦The packer at the fridge door LSU Whole box, half box, or a single item — and unwraps them coming back.
  • 🧭The receptionist Address_Decoder Book or fridge? Routes every request and merges every answer.
  • 🧊The walk-in fridge DMEM 8 KB, read/write. One beat slower than everything else.
  • 🥁The metronome clk_i Nothing is committed between beats. Only the rising edge counts.
The one-line version

A CPU is a machine that repeats one loop forever: look up the next instruction → work out what it means → do it → write the answer down → repeat. Everything below is detail hanging off that sentence.

02

Four beats to an instruction

Your CPU is multicycle: every instruction is broken into four short clock ticks instead of one long one. The Control Unit remembers which tick it's on and broadcasts it as state_o — the signal you can watch counting 0, 1, 2, 3 in every waveform.

Why not do it all in one beat? You could — that's a single-cycle CPU. But then the clock has to be slow enough for the worst instruction, and you need two separate memory ports because fetching and loading would happen in the same instant. Multicycle trades cycles for area, which is exactly the right trade for a student ASIC.

ELI5

It's a 4/4 drum beat. Look-it-up, understand-it, do-it, write-it-down. Then again. Forever. In a waveform you literally see state_o counting 0,1,2,3 and pc_o stepping once per group of four.

Gotcha · reset polarity

The Control Unit wants reset high to mean "stop". Everything else wants it low. That's the entire job of the lone inverterC block on your canvas — a translator between two people who agreed to signal "stop" in opposite directions.

03

Inside a 32-bit instruction

Every RISC-V instruction is exactly 32 bits — which is why the PC steps by 4 bytes. Think of it as a sentence where each word sits at a fixed position. Five different layouts reuse the same positions in different ways.

Decode one by hand. 0x00A00293 — addi x5, x0, 10 — breaks into imm=0x00A, rs1=0, funct3=000, rd=5, opcode=0010011. That reads as addi x5, x0, 10: bowl 5 gets bowl 0 (always zero) plus 10.

The Stage-5 bug lived right here

You first hand-encoded crcb with funct7 = 0100000 — but that pattern is already taken; it means SUB/SRA. The Control Unit correctly saw a subtract, and wb_sel_o never reached 3. The right encoding is 1000000. A custom extension has to claim an unused encoding, and the test failing proved the decoder was rejecting malformed CRC properly.

05

The map of the world

The CPU sees one flat address space, but only two regions are wired up. The Address_Decoder doesn't read the whole address — it checks the leading bits, like a postcode sorter, and routes accordingly.

ELI5 · why constants live in the recipe book

The book on the wall isn't only recipes. The back few pages are a reference table — oven temperatures, conversion charts. The cook reads from those pages the same way they'd read from a label in the fridge. So "go look something up" has to work in both places.

06

The bug worth telling in an interview

The firmware ran all 259 instructions and settled at 0x004003F4 — the FAIL address. The signal that looked wrong was a CRC result. The CRC unit was flawless.

StepWhat you looked atWhat you found
1Where pc_o settled0x004003F4 — the FAIL self-loop
2The first failing checkbne x10, x17 at 0x400374; x17 expected 0x1E82
3Where x10 came fromA chain of crcw ending at 0x400364
4What fed the CRCx6 and x7, both from lw at base 0x004003F8
5smoking gun the value of x60x004003F8 — the address itself, not 0x12345678
6The wire feeding LSU.mem_data_iCame from DMEM only. Rewired to the decoder. PASS
The whole bug in one sentence

The runner was only ever allowed to go to the fridge — so when the recipe said "look up the value in the appendix of the book", he came back holding the page number instead of the value.

Three things this teaches. First: the failing signal was a CRC result, but the CRC module was perfect — it was computing correct answers on garbage input. When a block produces a wrong answer, check its inputs before you check its logic. That instinct is the integration engineer's core skill.

Second: the "obvious" wiring was the wrong wiring. Loads read data memory is true 95% of the time and completely wrong here. The correct mental model is loads read whatever the address decoder decided the address points at.

Third: you never read 259 instructions. You found the failing branch, walked backwards through the data dependencies — x10 ← crcw ← x6 ← lw — and found the first value that was wrong. Four hops. Bisect by data, not by code.

07

How to read the waveforms

A waveform viewer is an oscilloscope for a simulated chip: every row is one wire, and time runs left to right. Multi-bit signals are drawn as stretched hexagons with the value inside — the pinch points are the moments the value changes. This is your Stage-4 capture, redrawn clean.

xRed x means undriven — nothing is sourcing that wire. Trace upstream to the first signal that goes x; that's the missing wire.
gapA multi-bit signal sitting flat and unlabelled is the value 0. The gap in rd_addr_i during sw is the store correctly writing no register.
flickerValues wobbling between clock edges are combinational muxes settling. Only the value at the rising edge is stored. Harmless.
blk36xxAuto-generated ChipInventor instance names. The readable signals nest underneath them — your register file is blk2832_43.
Reading the firmware verdict — watch one signalpc_o settles atx4Verdict
Firmware does addi x4, x0, 0 then jal x0, 00x004003EC0x00000000PASS
Firmware does addi x4, x0, -1 then jal x0, 00x004003F40xFFFFFFFFFAIL
ELI5 · why you don't read all 259 instructions

The test program's last act is to walk into one of two rooms and lock the door behind it — jal x0, 0 is a deliberate jump-to-itself. You don't watch the exam; you check which room it's standing in. On the waveform that's pc_o freezing on one value while state_o keeps ticking underneath. The CPU hasn't crashed. It's finished.

Reading a register you can't see. When the viewer won't expose registers[0:31], watch three signals together: rd_addr_i, rd_data_i and reg_we_i. Find the last rising edge where rd_addr_i equals your register number and reg_we_i is 1 — the value on rd_data_i at that instant is what the register holds. You can't open the cupboard, but you can log every delivery.

From circuit to silicon

Everything so far has been a description of a circuit and a simulation of that description. Neither is a chip. OpenLane is the toolchain that turns the description into a physical layout a foundry could actually print on 130 nm silicon.

Resolved — a mock IMEM was used, and it's disclosed

Earlier notes said the IMEM had to be swapped for a mock 3-instruction version before synthesis, then withdrew that advice when no mock existed. As of the 9 Sep 2026 export, a mock was introduced: IMEM_MOCK.v (3 instructions: addi x5,10 / addi x6,5 / add x7,x5,x6, default NOP) replaces IMEM_FIRMWARE.v, and DMEM_MOCK.v replaces DMEM.v — same ports, same wiring, contents only. This is disclosed here and in report section 4.8/4.12, per the requirement: the OpenLane GDSII was built from the placeholder program, not the 259-word official firmware. The full-firmware PASS result (o_PC = 0x004003EC, x4 = 0) is a separate simulation run against the real IMEM_FIRMWARE.v, described in FIRMWARE_AND_SIM.md — OpenLane proves manufacturability, the firmware sim proves correctness, and the report keeps them clearly labeled as two different runs. One extra note: DMEM_MOCK.v's comment claims "2048 words = 8 kB" but it's actually a 4-word (16-byte) array (DEPTH_W = 4) — harmless since the mock program never touches memory, but not literally 8 kB.

One red herring. The logs show designs/spm/. That's ChipInventor's internal staging folder — spm is OpenLane's bundled example design, reused as a working directory. DESIGN_NAME: "top" is what actually determines what gets built.
